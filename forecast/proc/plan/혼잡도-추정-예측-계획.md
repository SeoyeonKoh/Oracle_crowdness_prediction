# 혼잡도 추정·예측 작업 계획

## 개요
승하차 → 체류인원 → (예측) 미래 체류인원. 구역별 LOS로 접근성×혼잡 결합 판정에 사용.

## 진행 상황

### ✅ Phase 1 — 체류인원 계산 + LOS (완료)
- `src/config.py` 경로·시간상수·LOS 임계표
- `src/io_load.py` 인코딩/스키마 통합 로더(OA-12921·역사면적·OA-12928·CARD)
- `src/station_master.py` 역명 정규화·면적 조인·환승역 감지
- `src/occupancy.py` Little's Law 체류인원(비유료/유료)
- `src/los.py` 밀도→A~F 등급
- `src/validate.py` 볼륨·피크 교차검증
- `src/pipeline.py` end-to-end (`python -m src.pipeline`)
- 산출물: `output/occupancy_hourly.csv.gz`, `output/los_summary.csv`,
  `output/calc_validation.md`, `data/apex.sqlite`
- 방법론: `proc/research/혼잡도-추정-방법론.md`

### ✅ Phase 2 — 체류인원 예측 (완료)
- `src/model.py` 하이브리드: seasonal-naive(역×요일×시간)를 피처로 주입 + HGB가 월 계절성·상호작용 보정
  (역 273개 > 범주상한 255 → 타깃 인코딩 `sbase`·`snaive`로 수치화, 요일·시간·월·호선은 네이티브 범주형)
- `src/predict.py` 실행(`python -m src.predict`), 학습 2023–24 / 검증 2025 홀드아웃
- **결과**: occ_platform MAE **6.41** vs naive 6.67(+3.9%), corr 0.967 / occ_concourse 4.04 vs 4.18(+3.2%)
- 산출물: `output/prediction_metrics.md`, `output/prediction_sample.csv`, `data/model_occ_*.joblib`
- 한계: 캘린더 피처만 사용(승하차 실측 없이 예측). 연도 성장추세는 트리 외삽 불가 → 실시간 요인 확보 시 개선

### ✅ 기능 1 (혼잡도 예보) — 완료
사용자 담당 기능. 하위기능 1-1~1-5 + 실제 화면.
- `src/congestion_level.py` **1-2 4단계**(여유/보통/주의/혼잡, 밀도 분위수 p50/p80/p95) — LOS 포화 해결
- `src/service.py` 공통 서비스 계층(기능 2·3과 공유):
  - **1-1 도착 시점 예보**(`journey`) · **1-3 배지**(`forecast_at`, 평소 대비) · **1-5 출발 추천**(`recommend_departure`, ±1h) · 경로(`route`, 동일호선 역번호순)
- `src/causes.py` **1-4 원인**(공사/사고/지연/날씨) 인터페이스 + 데모 샘플(`input/causes.csv` 연동 가능)
- `src/export_forecast.py` → `output/forecast.json`(999KB, 11,340셀)
- `src/screen/`(index.html+app.js+style.css) 정적 예보 화면 — 실행법 `src/screen/README.md`
- 공통 출력 스키마 `{line,station,hour,platform/concourse:{density,percent,level,baseline,badge},causes}`
- **혼잡도 %** = 밀도 백분위(평일 분포), 4단계 경계=50/80/95%와 일관
- **전체 호선 통합 검색 + 환승 경로**: `service.route`(Dijkstra, 환승 4분), 화면은 전체역 datalist + JS Dijkstra
- **요일 월~일 + 공휴일**: `src/summarize_byday.py`(`holidays` 라이브러리) → `output/los_summary_byday.csv`
  - 학습: 공휴일 ≈ 일요일(상관 0.996), 평일의 0.52배 → 별도 카테고리
- 출발시각 5분 단위(시간 사이 선형 보간)
- 한계: 역간 2분·환승 4분 가정, 원인은 샘플(데이터 확보 시 교체)

### ✅ 기능 1 야간 고도화 (2026-08-03)
- **① 판단기준 재정의**: 추천 대표혼잡 = **승차지점(출발역+환승역) 혼잡 최댓값**(도착역 단독 아님). app.js `repMetric`
- **② 여러 경로 선택**: 환승 페널티로 최소시간·최소환승 대안 생성(`routeOptions`) + 화면 경로 선택 칩
- **③ 열차 30분 해상도**: OA-12928을 30분 슬롯(slotmin)으로 유지, 화면 30분 보간
- **⑤ 환승인원 통합**: OA-12033을 하차 프로파일로 시간분배(호선수 균등분할) → 유료구역 환승항 활성화(`pipeline.add_transfer`). 왕십리 8시 밀도 0.029→0.143
- **④ 절대 정원대비(첨두 모형) — 완료**: 순간 첨두 = 평균 + 승차×(배차/2)/60 (톱니 파형 최댓값). 첨두밀도÷정원밀도(CRUSH: 승강장1.5/대합실1.0 명/㎡, 튜닝)=정원대비%. `summarize_byday`에서 board·occ로 계산(파이프라인 재실행 불필요) → export pa/ca → 화면 '상대(백분위)/정원 대비(첨두)' 토글(휠체어는 더 보수적 ABS_BANDS). 포화 해소(강남 8시 26%). CRUSH는 면적평균 기준이라 가정값
- ⑤ 환승은 근사(환승 시간분포·호선분할 가정) — 실측 환승 시간대 데이터 확보 시 교체

### ✅ 열차 혼잡 컷 재설정 (2026-08-04 현장답사 반영)
- **용어 정정**: 보수적 = 위험을 크게 잡음 = "붐빈다고 본다". **정원 대비는 값이 낮게 나오므로 덜 보수적**
  (= 덜 안전한 쪽). "여유롭게 본다"와 "보수적으로 본다"는 정반대 — 팀 공용 정의로 고정
- **확인**: 열차 값은 **이미 정원 대비**(OA-12928 재차/정원 실측). 첨두 계산값은 승강장·대합실에만 적용.
  ⚠️ "정원 대비"가 두 군데 있고 출처가 다름 — 열차=실측 / 승강장·대합실=계산(가정)
- **문제**: 기준이 아니라 **컷**이 문제였음. 기존 여유 상한 일반 80%·휠체어 60% →
  동대문 40%(좌석 만석+입석 30명)가 두 프로필 모두 "여유"로 오답. 2호선 평일 97%가 여유로 포화
- **조치**: 좌석 만석선(정원의 약 34% = OA-12928 정원 정의의 좌석 비중)을 **여유의 끝**으로.
  `TRAIN_BANDS` 일반 [80,130,150] → **[34,80,130]**, 휠체어 [60,100,130] → **[20,34,60]**(제안값)
  - 근거 2겹: 데이터셋 정의(좌석≈정원 34%) + 답사 실측(왕십리 38·동대문 40·충무로 34에서 체감 갈림)
- **결과**: 동대문 40% → 일반 보통 / 휠체어 주의. 포화 해소(일반 여유 97%→43%, 휠체어 88%→21%)
- 미결: ① 충무로 34%가 경계에 정확히 걸림(`>34`이라 여유 유지) — 33 또는 이상(≥) 처리 검토
        ② 휠체어 컷은 제안값 — 휠체어 57%가 주의 이상이 되는데 현장 체감 대비 적정한지 확인 필요
