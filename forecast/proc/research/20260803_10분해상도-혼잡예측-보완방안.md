## 1. 현재 문제

**승하차 공개데이터가 1시간 단위라, 10분 단위 촘촘한 혼잡 예측이 근본적으로 어렵다.**

### 구체 시나리오
- 사용자가 "8:10 강남 출발"을 조회하면, 화면은 8시·9시 두 시간값 사이를 **직선으로 보간**해 8:10 밀도를 추정한다.
- 실제 승강장 혼잡은 열차 도착 직전 급증 → 도착 직후 급감(톱니)하며, 8:00~9:00 안에서도 크게 출렁인다. 직선보간은 이 시간 내(intra-hour) 변동을 전혀 못 담는다.
- 결과: "지금 붐빈다/한산하다"의 10분 단위 판단이 실제와 어긋날 수 있다.

### 원인 분석 (구성요소별 현 상태)

| 구역 | 원천 데이터 | 시간 해상도 | 현재 처리 | 코드 |
|------|-------------|-------------|-----------|------|
| 승강장/대합실 밀도 | OA-12921 승하차 | **1시간** | 1시간값 2개 **직선보간** ← 병목 | `densityAt` [web/app.js:75](../../src/web/app.js:75) |
| 정원대비(첨두) % | OA-12921 + 배차 **가정값** | 1시간 | 직선보간 | `absAt` [web/app.js:175](../../src/web/app.js:175) |
| 열차 내 혼잡 % | OA-12928 | 30분 | 30분 격자 보간 | `trainPctAt` [web/app.js:161](../../src/web/app.js:161) |

**핵심**: 무료 공개데이터로는 10분 미만 해상도의 "승하차/혼잡 원자료"가 존재하지 않는다(아래 §2 확인). 따라서 해법은 **① 1시간 총량은 그대로 두고, ② 시간 내 "형태(shape)"를 다른 고빈도 신호에서 빌려와 곱하는** 시간 분해(temporal disaggregation)다.

## 3. 방안 비교 (시간 분해 방법론)

목표: 1시간 승하차 총량 **합을 보존**하면서, 시간 내 10분 형태를 고빈도 신호에서 빌려온다.

### Option A: 프로파일 기반 분배 + 총량보존 스케일링 ⭐ 권장 (1순위)
과거 요일×시간대별 "10분 분배비율 프로파일"(합=1)을 학습해 1H 총량에 곱한다.

| 장점 | 단점 |
|------|------|
| 구현 단순, 해석 쉬움 | 고정 프로파일은 당일 이례(지연) 미반영 |
| **총량 자동 보존** (비율합=1) | → 실시간 신호로 보정 필요(Option C) |
| 며칠치만 있어도 동작, 쌓일수록 개선 | |
| 리스크 최저 | |

### Option B: 열차 도착 기반 톱니(sawtooth)/NHPP 모형 (2순위)
실시간 도착 API의 **실측 배차간격**을 꺾임점으로, 승객이 λ로 쌓이다 열차 도착 시 배출되는 톱니로 체류를 모델링.

| 장점 | 단점 |
|------|------|
| 물리적으로 타당(승강장 대기의 실제 형태) | 도착 API 안정 수집·파싱 필요 |
| 당일 배차 변동·지연 반영 | 승차/하차 비율 가정 필요 |
| ④ 첨두모형의 "배차/2" 가정을 **실측**으로 교체 | |

### Option C: Denton-Cholette (지표=실시간 인구/도착) (3순위)
총량 보존을 수학적으로 보장하며 실시간 지표의 "움직임"을 매끄럽게 반영. `tempdisagg`(Python)로 즉시 사용. 회귀계수 추정 불필요 → 짧은 표본에서도 안정.

### Option D: Chow-Lin / Litterman (4순위, 표본 축적 후)
실시간 지표와 총량의 통계적 관계를 GLS로 학습. **관측치(1H) 수가 충분해야** ρ 추정이 안정 → 수 주~수 개월 뒤 도입.

### 보류: Cubic spline 단독
음수·overshoot·모멘트 왜곡 위험. 승객수(양수·펄스형)에 부적합.

## 4. 권장안: "1시간 총량 × 10분 형태" 총량보존 분해 엔진 (A→B→C 단계 결합)

직선보간(`densityAt`)을 **프로파일×총량**으로 대체하고, 실시간 도착으로 톱니 보정, 기상·인구로 외생 보정하는 3층 구조.

**③ `src/batch/export_forecast.py` — 10분 형태 export**
현재 시간(hour) 셀만 내보내는 구조에, **요일×시간대별 10분 프로파일(6개 비율)** 을 추가 export.

**④ `src/web/app.js` — `densityAt` 교체**
```javascript
// 현재(직선보간)
return d0 + (d1 - d0) * (hf - Math.floor(hf));
// 제안: 시간 총량 × 10분 형태비율(총량보존)
const slot = Math.floor((totalMin % 60) / 10);          // 0~5
const w = cell(line,station,day,hour)?.profile10?.[slot] ?? 1;
return hourlyDensity * w;                                 // 합≈시간총량
```

## 6. 구현 단계 (점진 적용)

- **Phase 0 (지금·데이터 준비)**: 서버 jsonl 적재·파싱기 작성 → **배차간격 실측치** 산출. 며칠 축적 대기. *(선택한 "실시간 데이터 활용 준비")*
- **Phase 1 (무료·즉시)**: Option A 프로파일 분배로 `densityAt` 직선보간 대체(OA-12928 30분 형태 우선 활용, 도착 프로파일은 축적되는 대로).
- **Phase 2**: Option B 톱니 모형 — 실측 배차로 ④ 첨두모형의 "배차/2" 가정 교체.
- **Phase 3**: 기상청 외생변수 + citydata 인구 보정(Option C, Denton-Cholette).
- **Phase 4 (표본 축적 후)**: Chow-Lin 전환 / TMAP 10분 칸혼잡을 검증 라벨로.
- **모니터링**: 2026 국가중점데이터 "칸별 실시간 혼잡도" 무료 개방 시 최우선 채택.

## 7. 리스크 및 고려사항

- **총량보존 필수**: 어떤 분해든 `sum(10min slot) == 1H 총량` 검증 테스트를 둔다(음수·overshoot 금지).
- **표본 부족**: 서버 수집이 며칠~몇 주 쌓여야 프로파일·배차가 안정. 초기엔 OA-12928(30분) 형태로 대체.
- **커버리지**: 실시간 도착/위치는 서울 관할 구간 위주, citydata는 121개 장소 한정 → 미커버 역은 과거 프로파일 fallback.
- **하위호환**: forecast.json에 profile10 없으면 기존 직선보간으로 자동 fallback(화면 무중단).
- **유료 소스**: TMAP/SKT는 비용·계약 검토 후. 앱 크롤링은 배제.
- **정직 고지 유지**: 톱니·프로파일도 여전히 "추정"임을 README 신뢰도 표에 명시.
